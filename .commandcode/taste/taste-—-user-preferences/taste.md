# Taste — User Preferences
- Communicates feature requests as long, highly structured specs: numbered sections, ASCII/text flow diagrams, exact UI copy strings, and explicit API/schema shapes. Match that structure when implementing and reporting back. Confidence: 0.85
- Insists that every change preserves existing functionality — repeatedly states "do not break or remove any existing functionality" and "reuse existing architecture" instead of rewriting. Confidence: 0.95
- Strongly prefers extending existing models/services/middleware over creating duplicate or parallel systems; warns against "a second parallel" implementation of anything that already exists. Confidence: 0.9
- Wants the existing codebase inspected/analyzed before any code is written (e.g., "Don't start coding, first analyze it"; "Before coding, inspect the existing project"). Confidence: 0.9
- Requires all authorization, validation, and duplicate/ownership checks to be enforced on the backend; explicitly states frontend menu hiding / route guards are NOT security and that frontend-supplied role, user id, status, department, or permission values must never be trusted. Confidence: 0.95
- Expects automated tests for new features, including edge cases and per-role/per-API coverage; wants failures documented rather than silently fixed mid-testing. Confidence: 0.8
- Workflow: repeatedly asks the agent to turn off / stop the dev server(s) it is running and free the ports when finished (also asks to keep port numbers fixed). Confidence: 0.9
- UI taste: modern, clean, minimal, professional and mobile-first/responsive; prefers converting wide desktop tables into responsive card/list layouts on mobile rather than hiding columns with `display: none`. Confidence: 0.75
- Project convention: treat Asia/Dhaka (Bangladesh Standard Time, UTC+06:00) as the canonical timezone — store timestamps as UTC instants and convert to BST for display, never relying on server or browser local time. Confidence: 0.75
- Anti-fabrication/accuracy: documentation and copy (privacy policies, terms, help text) must be grounded in what the code actually does — explicitly forbids inventing features, data collection, third-party services, or security practices, and forbids over-claiming (e.g. never write "100% secure" or "we sell data" unless true). Confidence: 0.85
- For values that don't exist in the project (support email, phone, address, university name), wants clearly-marked, easily replaceable configuration placeholders surfaced in one central config file, never fabricated real-looking details — and unresolved gaps called out explicitly rather than silently filled in. Confidence: 0.8
- Verification/reporting workflow: expects the project's existing build/lint/test commands to be run after implementation with any resulting errors fixed, and a concise closing summary of files created/modified, routes added, actual data/services identified from the code, information still needing to be supplied by the owner, and the build/test result. Confidence: 0.8
- Editor/canvas UX: wants rich editors to feel like familiar desktop productivity apps — e.g. a "cell-row" table element built to behave like an MS Office/Word table, and layouts where the central canvas stays fixed/sticky while the side rails (pages, elements) scroll independently up and down with the mouse. Confidence: 0.6
